01What problem does it solve?

Why normal logging / APM tools aren't enough for AI apps

A normal web app has Sentry for errors and Datadog for metrics to answer "is it working?". LLM apps have problems those tools were never built for:

🎲 Non-deterministic

The same input gives different output every time. "Works on my machine" is meaningless — you must observe real production behavior, not reproduce it.

💸 Costs money per call

Every request burns tokens = real dollars. You need per-call, per-model, per-customer cost accounting, continuously.

🐢 Slow & spiky

LLM calls take 1–10s. Latency tails (p95/p99) are what users feel. You need percentile latency over time, not averages.

🤔 Quality is fuzzy

There is no "200 OK". An answer can succeed technically yet be wrong, rude, or hallucinated. Quality must be measured, not assumed.

🪆 Multi-step agents

One user question fans out into 5–20 LLM + tool calls. When it breaks, you need to know which step — and see its exact input/output.

📈 Volume is brutal

A busy AI product emits billions of these events. The storage and query problem alone is a serious distributed-systems challenge.

The one-liner to hold in your head

Respan captures every step your AI takes as a nested trace, stores it at massive scale, then (a) shows it to you as live dashboards + searchable logs, and (b) lets you score those traces for quality with code checks, LLM judges, and behavior models.

02The core concept: Traces & Spans

Understand this one data structure and the entire system clicks

A trace is the full story of handling one user request. A span is one step inside that trace. Spans nest into a tree and are typed — llm, tool, retrieval, agent. Every llm span records model, input, output, tokens, latency, cost, and status.

⚑ This is the keystone

The database schema, the SDK, the ingestion pipeline, and every screen in the UI exist to capture, store, and display these traces. Get the trace model right and everything else is aggregation or judgment layered on top.

04The wall every design hits: scale

Why a single Postgres (or bun:sqlite) collapses — and what the architecture is really solving

A demo can store spans in SQLite. A real company cannot. Here is the shape of the problem that forces every decision downstream:

Write amplification

One agent request = 5–20 spans. 10k requests/sec = 100k+ row inserts/sec, bursty and spiky. A row-store with indexes can't keep up.

Analytical reads

Dashboards ask "p95 latency per model per hour over 30 days" across billions of rows. That's a columnar-scan problem, not a point-lookup problem.

Fat payloads

A single prompt can be 100KB+ of context. Shoving blobs into your metrics store bloats it and wrecks compression.

⚑ The design principle behind everything below

Decouple, and use the right store for each shape of data. Fast dumb intake → durable buffer → batch writes into a columnar analytics DB; keep relational metadata in Postgres; keep big blobs in object storage; cache hot reads in Redis; run slow eval work on separate scalable workers. Kubernetes keeps all these stateless tiers alive and auto-scaled.

06Every component — how, why, what it solves

The "why does this box exist" tour. Remove any one and something specific breaks.

SDKClient SDK + wrapOpenAI

A thin library the customer installs. It wraps their model client and auto-captures every call as a span, batching them in memory and shipping asynchronously.

  • How Proxies chat.completions.create; builds spans; flushes batches over OTLP/HTTP on a background timer.
  • Why One-line integration beats asking customers to rewrite code. Async + batched = near-zero overhead.
  • Solves Capturing data without adding latency to — or risking the uptime of — the customer's product.

EdgeIngress / Load Balancer

The cluster's front door. Terminates TLS, routes paths, applies coarse rate-limiting, spreads traffic across ingest pods.

  • How K8s Ingress controller (e.g. NGINX/Envoy) in front of the ingest Service.
  • Why You never expose pods directly; you need one stable, secured entrypoint that scales horizontally.
  • Solves Even traffic distribution, TLS, and a choke point for abuse before it reaches your logic.

IngestCollector / Ingest service

Stateless pods that authenticate the API key, validate the payload, compute cost from token usage + a pricing table, offload fat payloads to object storage, then produce to Kafka.

  • How Horizontally-scaled deployment; does cheap CPU work only, holds no state.
  • Why Intake must be fast and dumb so it can soak spikes; anything slow (DB writes) is pushed past the buffer.
  • Solves Turning raw, untrusted, variable-size input into clean, enriched, uniform events.

BufferMessage queue — Kafka

A durable, partitioned log sitting between intake and storage. Producers write; multiple consumer groups read independently.

  • How Topics partitioned by project/tenant; consumers commit offsets; data retained for replay.
  • Why Decouples a bursty, spiky producer from a throughput-limited database; survives downstream outages.
  • Solves Spike absorption, zero data loss when ClickHouse is slow/down, replay after bugs, and fan-out to eval + alerting.

StoreClickHouse — analytics DB

Columnar, append-optimized database holding spans and pre-aggregated metrics. The engine behind every dashboard and log search.

  • How Consumers batch-insert tens of thousands of rows at once; materialized views pre-roll metrics by minute/hour.
  • Why Columnar storage scans and aggregates billions of rows in milliseconds and compresses them 10×+ — a row store (Postgres) can't.
  • Solves "p95 latency per model per hour over 30 days" over enormous volume, cheaply.

StoreObject storage — S3

Cheap, infinite blob store for oversized prompts and outputs; ClickHouse keeps just a reference.

  • How Ingest writes the blob, stores its key in the span row; UI fetches on demand.
  • Why Long-context payloads would bloat the analytics DB and destroy its compression and scan speed.
  • Solves Keeping the hot metrics store lean while still preserving full fidelity of every input/output.

StorePostgres — metadata

Relational, transactional store for everything that is small, mutable, and relational: users, projects, API keys, prompt versions, evaluator + dataset definitions.

  • How Standard managed Postgres; the serving tier reads/writes it for config and auth.
  • Why This data needs ACID transactions, updates, and joins — the opposite of append-only span data.
  • Solves Polyglot persistence: the right tool per data shape, instead of forcing one DB to do both jobs badly.

CacheRedis

In-memory store for hot dashboard query results, per-key rate-limit counters, and span-ID dedup.

  • How Serving tier checks Redis before hitting ClickHouse; ingest uses it for counters/idempotency.
  • Why The same dashboards are loaded constantly; recomputing identical aggregates wastes ClickHouse capacity.
  • Solves Sub-100ms repeat reads, abuse throttling, and exactly-once-ish handling of retried batches.

ComputeEval workers

A separate pool of workers that pull eval jobs from the queue, run code checks / call an LLM judge / score behaviors, and write results back.

  • How Own deployment + queue; scales on job backlog, independent of ingest/serving.
  • Why Evals are slow (LLM calls = seconds) and bursty; mixing them with intake would starve it.
  • Solves Running expensive quality scoring at scale without ever slowing live ingestion or dashboards.

ServeQuery API + Web app

Stateless pods that serve the dashboard UI and answer its queries from ClickHouse (metrics) + Postgres (config) + Redis (cache).

  • How Read-path services behind the same ingress; fan queries to the right store.
  • Why Separating read serving from write ingestion lets each scale to its own, very different load.
  • Solves Fast, independently-scalable dashboards and log search for users.

08The evaluation subsystem

"Unit tests for your AI" — the loop that lets a team ship prompt changes with confidence

Observability tells you what happened; evaluation tells you whether it was good. The workflow: build a dataset (often sampled from real production traces), define an evaluator, run it, and every score links back to the exact span it judged.

Code check

Deterministic & free: valid JSON, length limits, required substrings, regex. Instant, exact — use wherever possible.

LLM-as-judge

Another LLM grades against a rubric and explains itself. For fuzzy quality (helpfulness, correctness) that code can't check.

Behavior model

Describe a behavior in plain English ("hallucinated a fact", "refused unsafe request") → probability it's present. Scales to many behaviors cheaply.

09Monitors & alerting

Be paged before your users complain

A dedicated consumer group reads the same span stream and evaluates rules continuously: "error rate > 5% in 5 min", "today's spend > $500", "p95 latency > 8s". A matching rule fires through a dispatcher to Slack, email, PagerDuty, or a webhook. Because it reads from Kafka — the same buffer as storage — alerting keeps working even if the analytics DB is lagging, and adds no load to the query path.

Why a separate consumer, not a cron over ClickHouse?

Polling the analytics DB for alerts competes with user dashboards and adds latency to detection. Streaming evaluation off Kafka is real-time and isolated — a recurring theme: separate workloads get separate compute.

10The AI Gateway (the fourth pillar)

Optional, but it makes observability effortless

Respan also offers a gateway: one API endpoint that proxies to hundreds of models (OpenAI, Anthropic, …) with automatic fallbacks (primary down → retry on a backup), load balancing, response caching, and per-key spend limits. Because every call flows through the gateway, it produces spans into the same pipeline for free — no SDK needed.

11Kubernetes & the platform layer

What actually keeps all of the above alive, scaled, and shippable

Every stateless tier — ingest, consumers, eval workers, query API, web, gateway — runs as containers orchestrated by Kubernetes. The stateful stores (ClickHouse, Postgres, Kafka) usually run as managed services or dedicated operators, not naked pods.

Why Kubernetes here

  • Scale HPA auto-scales ingest & eval pods on CPU / queue-lag — handle a 10× spike, then scale back down to save money.
  • Heal A crashed pod is restarted and rescheduled automatically; rolling deploys ship with zero downtime.
  • Spread Multi-AZ scheduling survives a datacenter zone failure. One control plane, declarative config.

The rest of the platform

  • IaC Terraform provisions cloud + cluster; Helm/Argo deploys services — reproducible, reviewable infra.
  • CI/CD Build image → test → push to registry → progressive rollout, on every merge.
  • Meta Prometheus + Grafana + traces watch the platform itself — you must observe your own observability tool.

⚑ Honest engineering note

Kubernetes earns its keep because this system has many independently-scaling stateless services and real multi-tenant scale. K8s is about running the system reliably, not about the product's features — the trace/eval logic is identical whether it runs on one laptop or a 200-node cluster. Build the logic first; let the platform scale it.

12One request, end to end

Tying every box together in a single story

  1. A user asks the customer's agent a question. The agent makes several LLM + tool calls.
  2. The SDK captures each as a span, batches them, and fires them async at the ingress — the agent answers the user without waiting.
  3. Ingest pods authenticate, validate, compute cost, push any huge payload to S3, and produce the spans to Kafka.
  4. Storage consumers batch them and insert into ClickHouse; a sampler forks some onto the eval stream; the alert engine checks rules live.
  5. An engineer opens the dashboard; the query API serves it from Redis cache, falling back to ClickHouse + Postgres.
  6. They spot a bad answer, click into the trace (full payload lazy-loaded from S3), build a dataset, and run an evaluator on the eval workers.
  7. Scores come back linked to each span. They fix the prompt, re-run, watch the score climb, and ship — with a monitor now guarding the metric in production.
